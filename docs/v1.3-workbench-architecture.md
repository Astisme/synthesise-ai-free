# v1.3.0 Workbench Architecture Proposal

**Status:** Proposed architecture; implementation not started  
**Milestone:** v1.3.0  
**Scope:** A local-first product-development workbench around the existing Synthesise AI Free Agent Skill

## 1. Executive summary

The workbench should turn the repository's currently document- and prompt-driven product-development process into a visible, resumable workspace. It should not replace the canonical Agent Skill or silently fork its methodology. The skill remains the source of truth for stages, decision rules, templates and deliverable standards; the workbench provides project state, navigation, artifact management, evidence traceability and optional execution adapters.

The first release should be useful without model-provider credentials, network access or a hosted account. It should support a single user working on local projects, with explicit export/import so the project remains portable across agents and tools.

## 2. Product goals and non-goals

### Goals

- Create and reopen a project from a portable `PROJECT-BRIEF.md`.
- Present the lifecycle as navigable stages: discovery, opportunity selection, market research, validation, product architecture, curriculum/workbook, commercial design and launch.
- Capture assumptions, evidence, decisions, unresolved questions and next actions as first-class records.
- Link every important decision to its supporting evidence and originating stage.
- Generate and preview Markdown deliverables using canonical repository templates.
- Preserve user control over model calls, external research, file writes and exports.
- Run local structural and deterministic checks and show their results with provenance.

### Non-goals for the first release

- A hosted multi-tenant SaaS, team collaboration or user-account system.
- A replacement for Claude Code, Codex, Gemini CLI or other agent runtimes.
- An autonomous agent that researches, purchases services or publishes content without confirmation.
- A proprietary methodology fork or a new scoring formula.
- Mandatory provider APIs, telemetry, cloud sync or a database server.

## 3. Product principles

1. **Local-first:** project files live on the user's machine and remain readable without the application.
2. **Portable source of truth:** Markdown and ordinary files are authoritative; any index or cache is rebuildable.
3. **Canonical methodology:** stage instructions and templates are loaded from the skill package rather than copied into a second implementation.
4. **Evidence before claims:** distinguish facts, hypotheses, assumptions, decisions and recommendations; preserve source locators and verification metadata.
5. **Human approval:** show diffs and request confirmation before overwriting files, accepting consequential decisions or invoking external services.
6. **Optional intelligence:** model/provider adapters are plugins behind explicit user settings, never required for core operation.

## 4. Proposed user experience

The main shell has four areas:

- **Project switcher:** create/open projects, recent projects and import/export.
- **Lifecycle navigation:** stage list with status, dependencies, blockers and completion criteria.
- **Work surface:** stage-specific forms, evidence tables, decision log and generated artifact preview.
- **Activity/provenance panel:** changes, validation results, source links and pending approvals.

A project dashboard should answer: What stage is active? What is known versus assumed? Which decisions are blocked by missing evidence? What changed since the previous session? What is the next useful action?

Stages should be usable independently. Users can enter at any stage and can resume from existing project files without repeating discovery.

## 5. High-level architecture

```text
┌──────────────────────────────────────────────────────┐
│                  Desktop / Web UI                     │
│ Project switcher · Lifecycle · Evidence · Artifacts  │
└──────────────────────────┬───────────────────────────┘
                           │ typed application commands
┌──────────────────────────▼───────────────────────────┐
│                 Application services                  │
│ Project · Stage · Decision · Evidence · Artifact      │
│ Validation · Import/Export · Approval                 │
└───────────────┬───────────────────────┬──────────────┘
                │                       │
┌───────────────▼─────────────┐  ┌──────▼───────────────┐
│     Local project store     │  │ Execution adapters  │
│ PROJECT-BRIEF.md            │  │ Skill/CLI handoff    │
│ evidence/ decisions/        │  │ Optional model API   │
│ artifacts/ metadata/        │  │ Optional research    │
└───────────────┬─────────────┘  └──────────────────────┘
                │
┌───────────────▼──────────────────────────────────────┐
│ Canonical skill package + schemas + templates         │
│ Loaded read-only from the installed/repository source │
└──────────────────────────────────────────────────────┘
```

### Core modules

- **Project service:** discovers project roots, reads/writes project files, validates paths and maintains a project manifest.
- **Lifecycle service:** describes stages, prerequisites, outputs and handoffs. Definitions are mapped to canonical skill workflows.
- **Evidence service:** stores source metadata, claim status, verification method/date and links evidence to claims or decisions.
- **Decision service:** records selected option, rationale, alternatives, confidence, evidence links and review status.
- **Artifact service:** renders canonical templates into Markdown files, previews diffs and writes only after approval.
- **Validation service:** invokes the repository's local validators/evaluators as subprocesses, captures exit status and report paths, and never interprets fixture checks as proof of live-agent behaviour.
- **Adapter service:** optional integrations for agent CLIs or model APIs. Each adapter declares capabilities and permissions; no adapter is enabled by default.
- **Import/export service:** packages a project as ordinary files and checks compatibility when importing another version.

## 6. Project file layout

A project remains understandable in a text editor:

```text
my-product/
├── PROJECT-BRIEF.md
├── .synthesise/
│   ├── project.json
│   ├── decisions/
│   │   └── decision-0001.md
│   ├── evidence/
│   │   └── evidence-0001.md
│   ├── runs/
│   │   └── validation-2026-01-01.json
│   └── index.json
├── research/
├── deliverables/
│   ├── product-charter.md
│   ├── curriculum.md
│   └── launch-plan.md
└── exports/
```

`.synthesise/index.json` is a rebuildable index, not the authoritative content store. The project manifest records schema version, skill version, creation/update timestamps and relative paths. Dates in this example are illustrative only.

## 7. Data model

The initial domain model should include:

- **Project:** stable ID, title, audience, current stage, schema version and timestamps.
- **StageState:** stage ID, status, inputs, outputs, blockers and completion evidence.
- **Claim:** statement, epistemic state (observed, inferred, assumed, unknown), confidence and evidence references.
- **Evidence:** source ID, locator, source type, captured date, verification state, verification method and verified date.
- **Decision:** selected option, alternatives, rationale, status, owner (initially the local user), timestamp and evidence links.
- **Question:** unresolved question, impact, owner and next resolution action.
- **Artifact:** relative path, template/source reference, generated timestamp and content hash.
- **RunRecord:** command/adapter, configuration hash, timestamps, exit status and report/artifact references.

All file references must be relative to the project root, normalized and checked against path traversal and symlink escape. Secrets should not be written into project metadata or logs.

## 8. Interfaces and execution boundaries

The UI should call typed application services rather than shell commands directly. The validation service may execute only a configured allowlist of local commands, with explicit working directory and captured output. External model or research adapters must declare whether they transmit project data, what data is sent and whether costs may be incurred.

The initial integration path is deliberately simple:

1. Load the canonical skill and its stage/template references.
2. Prepare a stage-specific context bundle from the project files.
3. Let the user copy/export that context to a chosen agent, or invoke an explicitly configured local CLI adapter.
4. Import the returned artifact as a proposed change.
5. Display a diff and require approval before writing it into the project.
6. Run relevant local validation and attach the report to the project activity log.

The workbench must not claim that an agent executed a task unless it has a verifiable execution record. It must distinguish locally validated artifacts from model-graded or human-reviewed artifacts.

## 9. Security and privacy

- Default to local-only operation and no telemetry.
- Do not scan or upload arbitrary directories; ask the user to select a project root.
- Restrict reads and writes to the selected project and explicitly selected skill directory.
- Reject path traversal, absolute paths where not allowed, and symlink escapes.
- Redact secrets from diagnostic output where feasible; never request API keys in project documents.
- Show a data-transfer confirmation before any provider or research adapter sends content externally.
- Keep untrusted research content separate from instructions and label provenance.
- Require confirmation before overwriting or deleting user files.
- Make logs inspectable and avoid recording raw sensitive prompts by default.

## 10. Technology direction

The architecture is intentionally technology-neutral. A first implementation should choose one UI runtime and one local application boundary, rather than prematurely introducing distributed services.

Recommended decision criteria:

- Cross-platform installation and file-system integration.
- Reliable Markdown editing, preview and diff support.
- Typed domain contracts shared between UI and application services.
- Easy subprocess execution with bounded permissions.
- Straightforward automated tests and reproducible packaging.
- No required database daemon or hosted infrastructure.

A desktop shell around a web UI is a plausible first delivery; a browser-only application can be evaluated if its file-system limitations are acceptable. The final framework and language should be selected in a short implementation ADR after a prototype tests project-folder access, Markdown editing, diff review and CLI integration. Do not commit to a Java backend, Electron/Tauri shell or a hosted service before that spike supplies evidence.

## 11. Testing and quality strategy

- Unit tests for project paths, schema migration, lifecycle transitions, decision/evidence linking and artifact rendering.
- Contract tests ensuring stage definitions map to canonical skill files and template references.
- Golden-file tests for Markdown output and import/export round trips.
- Security tests for traversal, symlink escapes, unsafe overwrites and secret leakage.
- Integration tests using temporary project directories and fake agent adapters; no real API calls in required CI.
- End-to-end tests for create, reopen, resume, generate, review diff, approve and export.
- Existing deterministic skill evaluation remains a separate test layer; it does not validate UI behaviour or live model quality.

## 12. Phased delivery

### Phase 0 — architecture spike

Validate project-folder access, Markdown editor/preview, diff review, canonical skill discovery and one fake CLI adapter. Produce an implementation ADR and threat model.

### Phase 1 — local project shell

Create/open projects, parse and update PROJECT-BRIEF.md, show lifecycle stages, preserve decision/question logs and export portable files.

### Phase 2 — evidence and artifact workflows

Add evidence/claim linking, decision records, canonical template rendering, artifact previews and approval-based writes.

### Phase 3 — validation and agent handoff

Integrate local validators, capture run reports, support copy/paste and optional local CLI adapters with explicit permissions.

### Phase 4 — optional provider adapters

Only after privacy, cost and consent controls are tested, add opt-in model/research providers. Provider calls remain outside required CI.

## 13. Acceptance criteria for v1.3.0

The proposal is ready for implementation planning when:

- The architecture and non-goals are reviewed and approved.
- The canonical-skill boundary and portable project format are preserved.
- A prototype demonstrates safe project-folder access, Markdown preview and diff-based writes.
- A threat model covers local file access, untrusted research and optional external data transfer.
- An implementation ADR selects the UI/runtime stack based on prototype evidence.
- A test plan separates deterministic repository checks from workbench UI tests and live-agent evaluation.

## 14. Open decisions

1. Desktop shell versus browser-first local application.
2. Whether the first version should support multiple agent CLIs or only copy/paste handoff.
3. Whether project state beyond Markdown should use a rebuildable JSON index or remain entirely file-derived.
4. Which stage-level forms provide enough value to justify structured UI rather than Markdown editing alone.
5. Packaging and auto-update strategy across Windows, macOS and Linux.

These decisions should be resolved through the Phase 0 spike, not assumed in advance.
